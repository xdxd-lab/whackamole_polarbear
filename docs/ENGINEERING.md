## 1. 測試只看玩家看得到的結果

早期的檢查是比對程式碼裡有沒有某段字串。這種檢查有兩個毛病：整理程式碼就會失敗（誤報），而真的把規則改壞了卻可能照樣通過（漏報）。19.0.0 起全部換成行為測試。

測試打開真的瀏覽器、載入真的頁面，然後只觀察玩家感受得到的東西：畫面上的分數與文字、元素的位置與大小、發出的音效、震動、存在瀏覽器裡的最高分。**不讀取遊戲內部的變數，也不比對原始碼。**

要讓這種測試穩定，有三件事是關鍵：

- **時間與亂數由測試控制。** 頁面載入前先注入假的時鐘與亂數（`tests/support/page-init.js`），測試用「前進 850 毫秒」「下一個亂數是 0.2」來推進遊戲。同樣的輸入永遠得到同樣的一局，沒有「偶爾失敗」。
- **整局重播比對。** `tests/golden/*.trace` 是五局完整遊戲的逐行紀錄（什麼時候哪個洞出現什麼、分數怎麼變）。任何改動只要讓其中一行不同，測試就失敗。這是防止「不小心改到玩法」最有效的一道。
- **需要重錄哪種資料，決定版號進哪一段。** 要重錄整局重播，代表玩法變了（主版）；只要重錄畫面狀態，代表看起來變了（次版）；什麼都不用重錄才是修補版。版號因此不靠感覺決定，見 [VERSIONING.md](./VERSIONING.md)。

另外保留一個不用假時鐘的冒煙測試（`scripts/verify-assets.mjs`）：用真實時間跑一小段，確認頁面在沒有任何測試替身的情況下真的能玩。假時鐘會遮住「真的瀏覽器裡計時器行為不同」這類問題。

## 2. 突變檢查：測試那些測試

測試全部通過，只說明程式符合測試，不說明測試夠嚴格。`scripts/mutation-check.mjs` 反過來檢查測試：

- **突變項目（MUTANTS）**：故意把一條規則改壞，例如把「企鵝 +1」改成 +5、把某條 CSS 規則拿掉。整套測試**必須失敗**。如果沒失敗，代表這條規則沒有被任何測試保護。
- **等價項目（EQUIVALENTS）**：只改寫法不改行為，例如把 `.12` 寫成 `0.12`、把腳本搬到另一個檔案。整套測試**必須通過**。如果失敗，代表測試綁住了寫法，以後重構會被誤擋。

每新增一個行為，就補一個「把它改壞」的突變項目。目前有一百多項。

### 過時項目要當成錯誤

每個突變項目靠一段搜尋字串找到要改的地方。程式碼正常修改後，字串可能找不到了，這個項目就悄悄失效。CI 用 `--strict`，找不到字串直接算失敗，保護範圍才不會默默縮小。

還有一個更隱蔽的情況：**搜尋字串出現不只一次**。取代只改第一處，改到的可能不是原本想測的那一處，結果這個項目「通過」了卻沒在測它該測的東西。所以改過既有程式碼之後、推送之前，要確認每個搜尋字串在 `index.html` 裡恰好出現一次。

### 每個項目都要跑整套測試，所以很重

- 一個項目大約要一分鐘，全部跑完要一個多小時的機器時間。CI 把清單切成 5 組、分給 5 台機器平行跑，每台一次只跑一個項目。
- **不要在開發用的電腦上跑完整清單，更不要平行跑。** 每個項目都會開瀏覽器，同時開很多個會把機器拖垮。本機只用 `--only "<項目名稱>"` 跑剛新增或剛改到的那幾項，一次一個。
- 程式遇到不認得的參數會直接停下。這是刻意的：早期版本會忽略打錯的參數，然後開始跑完整清單。

### 突變檢查教會我們的事

突變項目沒被抓到時，通常不是程式錯，而是測試的假設錯了。兩個實例見[踩過的坑](#9-踩過的坑)的「CI 的字型比較窄」與「改了版面，舊的突變項目失效」。

## 3. 三種瀏覽器

同一套檢查在 Chromium、Firefox、WebKit 各跑一次，三者都必須通過才能合併。突變檢查只在 Chromium 跑（它測的是測試本身，跑三次沒有額外價值）。

用環境變數 `WAM_BROWSER` 選瀏覽器，預設是 Chromium；各瀏覽器已知的差異寫在 `tests/support/browser.mjs` 的註解裡。實際遇到的差異：

- **Firefox 在 Linux 上需要音效伺服器，Web Audio 的時間才會前進。** CI 的機器沒有音效卡，結果音樂「開始了」卻永遠不淡出、不結束，相關測試全部逾時。解法是在 CI 啟動 PulseAudio 並建立一個靜音的虛擬輸出。
- **WebKit（Playwright 版）不使用 HTTP 快取。** 「十分鐘內重複造訪不重新下載圖片」這項測試在 WebKit 上無法成立，所以只在這個引擎跳過，並在程式裡寫明原因。跳過要有具體理由並寫在跳過的地方，不能只是「它會失敗」。
- **瀏覽器的建置版本跟著作業系統版本。** 測試工具提供的 Firefox、WebKit 只支援特定的 Ubuntu 版本。CI 的 `ubuntu-latest` 升級後可能還沒有對應的版本，所以這兩個工作固定在 `ubuntu-24.04`。
- **版面差異是真的。** Firefox 曾經在矮螢幕上讓棋盤維持原尺寸、把按鈕擠出畫面（19.1.2 修正）。只在一種瀏覽器測版面，等於沒測另外兩種的玩家。

讓新引擎從「先觀察」到「必須通過」的做法：工作矩陣裡每個引擎有一個 `experimental` 欄位。標成 `true` 時，失敗只留下警告、不擋合併，可以先收集它在 CI 上失敗的清單；清單清空後改成 `false`。現在三個引擎都是必須通過。

有些瀏覽器在特定的開發機作業系統上啟動不了。遇到時不要花時間修本機環境：本機跑 Chromium，其他兩種看 CI 的結果與截圖。

## 4. CI 的設計

流程在 [`.github/workflows/verify.yml`](../.github/workflows/verify.yml)，共 8 個工作，全部是 `main` 的必要檢查：

```
Chromium 把關 ──┬── WebKit 把關
               ├── Firefox 把關
               └── 突變檢查 1/5 … 5/5
```

- **先跑最便宜的。** Chromium 把關只要幾分鐘。它沒過，後面七個工作就不啟動，不浪費機器時間。
- **第三方 Action 用完整的 commit 雜湊固定版本**，旁邊註明對應的版號。標籤可以被移動，雜湊不行。
- **權限最小化。** 工作流程只有 `contents: read`。
- **每個工作都有逾時上限。** 卡住的工作幾分鐘內結束，而不是佔用機器六小時。
- **截圖是給人看的產出。** 每次執行都為 16 種螢幕尺寸拍下開始畫面與遊戲中的畫面，三種瀏覽器各一份，隨工作結果上傳。審查版面改動時看的是這些圖，不是想像。拍截圖的步驟用 `if: always()`，測試失敗時反而最需要看圖。
- **截圖前先凍結動畫。** 淡出中的浮字、擴散中的光圈，每次拍到的時間點不同，圖就無法比較。截圖腳本把動畫停在固定的進度再拍。

### 讓 CI 不被外部服務拖垮

瀏覽器需要的系統套件要從 Ubuntu 的套件伺服器下載。伺服器連不上時，所有工作在跑到第一個測試之前就失敗了，而且預設要等十幾分鐘才放棄。`scripts/ci/system-libraries.sh` 做了三件事：

1. 下載過的套件存進快取。之後在同一個機器映像上執行時，直接從快取安裝，完全不需要網路。
2. 把下載的逾時縮短到幾十秒，失敗得快。
3. 第一次失敗後，把連不上的鏡像站從清單移除，第二次改連官方站。

快取的鍵值包含「機器映像版本」與「測試工具版本」，其中一個變了就重新下載，不會用到過期的套件。

### 分組數量寫在兩個地方

突變檢查的工作名稱是 `Mutation check 1/5` 到 `5/5`，而分支保護規則是用**名稱**指定必要檢查的。改分組數量時，工作名稱跟著變，舊名稱的檢查永遠不會再出現，合併就卡住了。正確的順序：先讓新名稱的檢查在 Pull Request 上跑出結果，再改保護規則，最後合併。

### 區分「程式的失敗」與「環境的失敗」

CI 失敗時先分類：

- **程式或測試的問題**：測試的斷言失敗、突變項目沒被抓到。要改程式或測試。
- **環境的問題**：套件伺服器連不上、上傳產出失敗、機器被回收。重跑即可，但要記下來；同一種環境問題出現第二次，就值得像上面那樣處理掉。

我們的合併條件是「最後要合併的那個 commit，CI 第一次執行就全部通過」。重跑才通過的結果不直接採信，先弄清楚第一次為什麼失敗。不穩定的測試如果被重跑蓋過去，之後每一次失敗都會被當成「又是那個不穩定的」。

## 5. 版面與字型

遊戲不能捲動，所以每個控制項都必須在畫面內而且點得到。`tests/layout.test.mjs` 在 16 種螢幕尺寸（`tests/support/viewports.mjs`，直式與橫式手機、平板、桌機）上逐一檢查：元素的方框在畫面內、從中心點點下去真的點得到它、頁面高度不超過螢幕。

幾條從修問題得到的規則：

- **用「加上它前後，其他東西的位置不變」來測「不佔空間」。** 頁尾的致謝、練習局的標記都不該擠到棋盤。測試先量位置，隱藏或顯示該元素，再量一次，兩次必須相同。
- **元素依自己拿到的寬度調整，用 container query，不用螢幕寬度。** 頁尾的寬度不只取決於螢幕寬度，還取決於直橫與版面模式。問「螢幕多寬」是間接的，問「我自己多寬」才準。
- **文字的寬度每台機器都不一樣。** 同一段字在不同作業系統、不同瀏覽器上，寬度可以差到一成。因此：
  - 測試不要斷言「這段字剛好放得下」。在一台機器上放得下，在另一台未必。
  - 樣式不要寫死「寬度小於某個數字就換成短版」來處理文字放不下的問題。那個數字是在某一台機器上量出來的。
  - 真的要依「放不放得下」切換顯示時，讓頁面在執行時自己量（21.2.2 的音樂致謝就是這樣做），並在視窗大小改變、字型載入完成後重新量。
  - 測試跟著同一個原則寫：不預期特定寬度，而是檢查「放得下就必須完整顯示、放不下才顯示短版、顯示出來的都沒有被截斷」。

## 6. 發布流程

合併到 `main` 就會發布到 GitHub Pages，沒有預備環境。所以所有把關都在合併之前。

1. **版號只有一個來源**，是 `index.html` 裡的 `VERSION`。頁尾、README、CHANGELOG 的寫法由 `tests/version.test.mjs` 自動核對，不一致就不能合併。人工核對版號遲早會漏。
2. **版號與 CHANGELOG 在同一個 Pull Request 裡改好。** 不能合併後再補，因為合併就上線了。
3. **日期是合併當天。** Pull Request 放過夜，日期就錯了：合併前要改日期並重新跑完 CI。
4. **合併前重新核對條件。** 就算已經說好「CI 通過就合併」，動手前仍然重新查一次：要合併的 commit 是不是當初說的那個、檢查是不是全部通過而且是第一次執行、有沒有衝突。從說好到動手之間，分支可能已經變了。
5. **用 merge commit 合併**，在那個 commit 上打標籤、建立 Release，內容直接取自 CHANGELOG 的那一段。標籤、Release、CHANGELOG 三者一一對應。
6. **上線後確認。** 打開線上網址看頁尾的版號。網址後面加一個隨機的查詢參數，避免看到快取的舊版。

### 快取與檔名

GitHub Pages 讓瀏覽器把檔案快取 10 分鐘。如果同一個檔名換了內容，玩家可能拿到新的網頁配舊的圖片。所以圖片與音樂的檔名帶有內容雜湊（例如 `bear-45461a4e9175.avif`）：內容變了，檔名一定變。`index.html` 裡同時記錄圖片的 SHA-256，載入時核對，內容不符就不開始遊戲，而不是顯示壞掉的畫面。

### 文件、測試與 CI 的改動不進版

玩家拿到的遊戲完全一樣時，不改版號、不打標籤。這讓版號維持「玩家看得到什麼變了」的意義。

## 7. 素材與授權

- **用之前先讀來源頁面上的授權，用的時候再確認一次。** 授權寫在素材的來源頁面，不是寫在搜尋結果或轉載的地方。
- **把出處記成資料。** 每首音樂的曲名、作者、來源網址、授權、檔案雜湊都在 `deployment/music.json`。測試會核對頁面上的致謝與這份清單一致，所以新增或移除曲目時不會漏改致謝。
- **CC0 不要求署名，但我們仍然署名。** CC0 是作者無條件放棄權利，來源頁面上的「希望的署名方式」是作者的期望而不是條件。照著寫沒有成本，也是對作者的尊重。相對地，CC BY 之類的授權，署名是使用的條件，漏了就是違反授權。兩者要分清楚。
- **記下對原作做了什麼。** 擷取哪一段、音量調了多少，都寫在 [CREDITS.md](../CREDITS.md)。日後有人問「這和原曲一樣嗎」時有答案。
- **移除的素材也留下紀錄。** 用過又拿掉的曲目，在 CREDITS 留一行說明什麼時候移除、為什麼。
- **公開不等於可以任意取用。** 角色圖是這個專案自己的素材，不是 CC0。repository 公開只代表看得到；能不能拿去用，以 repository 標示的授權為準，沒有標示時依著作權法預設為保留所有權利。

## 8. 音樂的音量

四首曲子來自不同作者，原始音量差很多。讓它們聽起來一樣大聲，比想像中難：

- **先用標準的響度量測對齊**（-18 LUFS）。這一步讓數字一致。
- **數字一致不等於聽起來一致。** 響度量測會把重低音算進去，但手機與筆電的小喇叭幾乎發不出 300 Hz 以下的聲音。低音多的曲子，量起來夠大聲，實際聽起來卻小很多。所以再用「300 Hz 以上的響度」對齊一次（`scripts/music/speaker.py`）。
- **最後用耳朵確認，而且一次只聽一首。** 連續播放時，耳朵會適應前一首的音量。逐首單獨播放、中間停頓，才聽得出差異。
- **先聽內容，再做整合。** 曾經整合完一首曲子才發現它不適合這個遊戲，整合的工夫白費。現在的順序是：先聽、確認要用，才處理檔案與寫程式。

格式上，每首提供 Ogg Opus 與 AAC 兩種，因為 18.4 以前的 Safari 不支援 Ogg Opus。圖片同理：AVIF 為主，另備 WebP 與 PNG，舊裝置也能顯示。

## 9. 踩過的坑

### CI 的字型比較窄

**現象**：一個突變項目把「小螢幕隱藏日期」的規則拿掉，預期測試失敗，本機確實失敗，CI 上卻通過。

**原因**：測試檢查的是「頁尾第一行有沒有折成兩行」。CI 機器的字型比較窄，就算日期沒隱藏，一行也放得下。

**修正**：直接檢查規則本身（頁尾窄於某寬度時，日期的 `display` 是不是 `none`），不透過「有沒有折行」這個會隨字型改變的結果去推論。

**通則**：測試要檢查你真正在意的那件事。透過副作用間接檢查，副作用不出現時測試就失明了。

### 用固定門檻處理「文字放不下」

**現象**：為了最小的螢幕把致謝換成短版，條件寫成「頁尾窄於 270px」。結果另一個尺寸的頁尾是 268px，四個名字明明放得下，也被換成短版。

**原因**：270 是看著一台機器的量測結果訂的，訂的時候沒有把每個尺寸代進去核對。即使訂對了，換一種字型還是會錯。

**修正**：拿掉門檻，改由頁面量測名字實際的寬度。

**通則**：條件是「放不放得下」，就去量放不放得下，不要用另一個數字去近似它。訂任何門檻之前，把已知的每個案例代進去算一次。

### 改了版面，舊的突變項目失效

**現象**：上面那次修改之後，另一個不相關的突變項目（「作者很多時折成兩行」）不再被抓到。

**原因**：原本靠最小的螢幕上名字超出寬度來抓到折行。修改後那個螢幕改顯示短版，「名字超出寬度」的情境消失了。

**修正**：新增一個不依賴現有名單長度的測試：在測試裡多加兩位作者，確認名字會縮短而不是折行。

**通則**：測試如果依賴「目前的資料剛好會觸發」，資料或版面一改就失效。讓測試自己製造它需要的情境。這也是保留完整突變檢查的理由：這種失效只有它抓得到。

### 把規則改壞的檢查，自己也會過時

**現象**：發版時把版號從 `x.y.1` 改成 `x.y.2`，突變清單裡有一項是「把版號改成 `x.y.2`」，於是它變成沒有任何改動的空操作。

**修正**：突變清單裡含版號的幾項，發版時要跟著改；這寫進了發版步驟，並由 `--strict` 的過時檢查把關。

**通則**：測試資料裡寫死的「現在的值」，在值改變時要有機制提醒你。

### 套件伺服器故障讓所有工作失敗

見 [讓 CI 不被外部服務拖垮](#讓-ci-不被外部服務拖垮)。**通則**：CI 依賴的每一個外部服務都會有故障的一天。能快取的就快取，不能快取的至少要快速失敗。

### 在開發機上跑完整的突變檢查

**現象**：平行跑幾十個項目，每個都開一個瀏覽器，整台機器停止回應。

**修正**：程式預設一次只跑一個；完整清單只在 CI 跑；本機用 `--only`。

**通則**：重的檢查要有安全的預設值。「記得加參數才不會出事」的工具，總有一天有人忘記。

### 切換分頁時遊戲繼續倒數

**現象**：玩家切到別的分頁再回來，這一局已經結束了。

**修正**：分頁隱藏時暫停，回來後由玩家按「繼續」（20.0.0）。這改變了一局的實際時間，所以是主版。

**通則**：瀏覽器在分頁隱藏時會降低計時器的頻率，依賴計時器的遊戲邏輯要明確處理「看不見的時候」該怎麼辦，而不是交給瀏覽器的預設行為。

### 最高分紀錄的相容性

每個難度各自記錄最高分（21.0.0）時，「普通」沿用原本的儲存名稱，其他難度在後面加字尾。舊玩家的紀錄因此自動成為「普通」的紀錄，不需要轉換程式，也不會消失。

**通則**：改儲存格式之前，先想舊資料會怎樣。最好的遷移是不需要遷移。
