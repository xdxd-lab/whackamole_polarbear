# 版號規則

這份文件說明雪地敲敲樂的版號怎麼決定、寫在哪裡、發版時要做什麼。從 19.0.0 起適用。

## 版號長什麼樣子

版號是三個數字：`主版.次版.修補版`，例如 `19.1.0`。對外可以只說主版，寫成 `V19`。

這是 [Semantic Versioning](https://semver.org/lang/zh-TW/) 的寫法，但遊戲沒有給別的程式用的介面，所以「不相容」改以玩家的角度定義：**同樣的玩法、同樣的分數還能不能互相比較**。

## 什麼變更進哪一段

判斷時從上往下看，符合的第一項就是答案。一次發版包含多種變更時，取最高的那一段。

| 進哪一段 | 什麼時候 | 例子 |
|---|---|---|
| **主版** `20.0.0` | 玩法或計分改了，新舊分數不能再放在一起比；或是玩家存的最高分會消失 | 改分數、機率、出現與停留的毫秒數、每局秒數、難度的數量或設定；改 `BEST_KEY` |
| **次版** `19.1.0` | 玩家看得到、聽得到的新東西或改動，但玩法與計分不變 | 新畫面效果、背景音樂、新的或重畫的角色圖、版面調整、新的設定選項 |
| **修補版** `19.0.1` | 修正錯誤或改善效能，玩家不應該感覺到設計上的改變 | 修版面被切掉、修錯字、縮短載入時間、圖片重新壓縮但看起來一樣 |
| **不進版** | 玩家拿到的遊戲完全一樣 | 測試、CI、文件、重構（所有測試不需更新就通過） |

進主版時，次版與修補版歸零；進次版時，修補版歸零。

### 用測試來判斷

拿不定主意時，看這次變更需要重錄哪些測試資料：

- 需要重錄 `tests/golden/*.trace`（整局重播），或需要改 `tests/rules.test.mjs` 裡的分數、機率、時序 → **主版**。
- 只需要重錄 `tests/golden/visual-states.json`（畫面狀態），或新增畫面相關的測試 → **次版**。
- 什麼都不用重錄，只是讓原本就該通過的行為通過 → **修補版**。

### 最高分紀錄（`BEST_KEY`）

- `BEST_KEY` 是玩家瀏覽器裡存最高分的名稱，目前是 `wam_best_20260904v7`。這個名稱和版號無關，**進版時不要跟著改**。
- 只有在計分方式改變、舊的最高分不再有意義時才換新的名稱，這一定是主版，而且要在 CHANGELOG 寫明「最高分會重新計算」。
- 能轉換舊紀錄就轉換，不要直接丟掉。

### 圖片與聲音素材

- 素材資料夾與檔名用的是「內容的日期與雜湊」（例如 `assets/v16-20260909/bear-45461a4e9175.avif`），不是遊戲版號。素材沒換，資料夾就不改名。
- 換了內容就要換檔名。GitHub Pages 會讓瀏覽器把檔案留 10 分鐘，同一個檔名放不同內容，玩家會拿到新舊混在一起的遊戲。
- 玩家看得出或聽得出差別 → 次版；看不出差別（重新壓縮、換格式）→ 修補版。
- 新素材要同時更新 `deployment/` 裡的清單與 `index.html` 裡的雜湊，自動檢查會核對。

## 版號寫在哪裡

唯一的來源是 `index.html` 裡的 `const VERSION = '19.0.0';`。下列地方必須和它一致，`tests/version.test.mjs` 會自動檢查前四項：

| 位置 | 寫法 |
|---|---|
| `index.html` 的 `VERSION` | `19.0.0` |
| `index.html` 頁尾 | `版本 19.0.0（2026-11-10）` |
| `index.html` 的 `<title>` | 結尾是 `V19`（只寫主版） |
| `README.md`「目前版本」 | `**V19（19.0.0，2026-11-10）**` |
| `CHANGELOG.md` 最上面一筆 | `## [19.0.0] - 2026-11-10` |
| `scripts/mutation-check.mjs` | 名稱裡有 `version` 的幾個突變項目，內含目前的版號與日期 |
| git tag 與 GitHub Release | `v19.0.0` |

日期是合併到 `main` 那一天（台北時間），格式 `YYYY-MM-DD`。`package.json` 只是測試工具的設定，不寫遊戲版號。

## 發版步驟

合併到 `main` 就會上線到 GitHub Pages，所以版號要在同一個 Pull Request 裡改好，不能事後補。

1. 依上面的表決定新版號。
2. 改 `index.html` 的三處、`README.md`、`scripts/mutation-check.mjs` 裡的版號與日期。
3. 在 `CHANGELOG.md` 最上面加一筆，用玩家看得懂的話寫，分成「新增」「變更」「修正」「移除」；只影響開發的放在「給開發者」。最下面補上該版的連結。
4. 等 CI 全部通過（包含突變檢查）再合併，使用 merge commit。
5. 合併後在那個 merge commit 上打標籤並建立 Release，內容貼上 CHANGELOG 的那一筆：

   ```sh
   git tag -a v19.0.0 -m "V19 (19.0.0)" <merge commit>
   git push origin v19.0.0
   gh release create v19.0.0 --title "V19 (19.0.0)" --notes-file <那一筆 CHANGELOG>
   ```

6. 打開線上網址，確認頁尾的版號與日期是新的。

不進版的變更（測試、CI、文件）直接合併，不改版號、不打標籤。

## V18 到 V19 怎麼對應

V1 到 V18 用的是單一流水號：每次發布加一，不分大小，日期另外寫（例如 `20261024-v18`）。這套寫法看不出一次發布是改了規則還是只修了錯字。

- **V19 = 19.0.0**，是新規則的起點。主版沿用原本的流水號，所以玩家看到的仍是「V18 的下一版是 V19」。
- 若嚴格套用新規則，V18 之後的變更（版面修正、減少動態、敲擊回饋、外觀打磨）沒有動到玩法與計分，只算次版。但 V18 沒有次版與修補版可以接續，所以這一次以 `19.0.0` 作為基準，之後才依規則遞增。
- 舊的 `V1`–`V18` 不回頭改寫，也不補打標籤；CHANGELOG 裡保留原來的寫法。
- 接下來的例子：加入背景音樂是 `19.1.0`；之後修一個版面錯誤是 `19.1.1`；哪天調整分數或機率就是 `20.0.0`。
